# Core holdings and brokerage cash freshness

The owner authorized the specific Core removal repair identified in the C1 reliability review. In a fictional account using the published portfolio and account handlers, the opening review returned three checked purchases. A newer Core row date correctly blocked them. A conditional portfolio save removing that row erased the only freshness evidence and the same broker observation returned three checked purchases again. The broker balance, strategy rules and market inputs were unchanged.

The portfolio route now keeps Core edit timestamps in the same strong-ETag write as the holdings snapshot. Additions, quantity and basis changes, removals and transitions into or out of Core all count. Reordering, Swing-only changes and cash pseudo-positions do not create a new timestamp. If a save would drop a dated Core row or clear its legacy date, the existing date survives in the same document. The server never uses an edit as evidence of a cash movement. Existing portfolio documents require no migration. A Core removal that happened before this release and already lost its only evidence cannot be reconstructed from the current snapshot.

The existing corrected-account purchase check compares each Core edit with the brokerage observation used for that check. A retained recommendation's previously verified cash still applies to a completed fill executed before a later Core change. Multiple later edits do not erase an earlier cutoff. The check saves no account flag, fill, journal entry or brokerage observation. The usual newer brokerage cash observation, existing financial reconciliation and all opening, event and risk checks still govern eligibility. The approved account recovery and historical replay are unchanged.

Home hides existing checked buys and adds immediately when the local Core holdings change. A synced and verified opening response restores purchase display only when the existing checks pass. Existing Sell and stop recommendations and the completed-trade recorder remain available. A would-issue Buy also verifies the current saved portfolio once more after provider work. If a Core save was committed during that work, the request reuses its own opening evidence to recompute with buying blocked. Another device's edit after this final verification is outside that response's as-of boundary. The next account verification checks current saved evidence.

- Run the real portfolio/account API fixture against strong ETags, legacy dates, every Core edit, a mid-review change, before-edit and after-edit fill timing, and the existing material-difference check. Require no financial mutation from a holdings edit and equivalent protected sells and checked purchases for equivalent verified inputs.
- Run the normal Home/App Chrome rehearsal including its Core-removal case. Observe a withheld portfolio save, a successful conditional save, stale-cash suppression in the next opening review, and the same checked quantities after a newer broker cash observation through the existing form. The fixtures use fictional holdings and store and market boundaries.
- Require the frozen application hashes, canonical integrity, complete regression suite, optimized build, dependency audit and all four exact-head CI jobs. Verify the matching preview, same merged tree, canonical production release identity and read-only readiness. Verify actual-account behavior only if passive authorized evidence becomes available through normal use. Never exercise live account mutation or producers to verify release.

## Rollback

Keep the `coreCashChangeTimes` field and its conditional writer if purchase presentation needs a subsequent correction. The older writer replaces the portfolio document and can discard this field on its next successful save. Avoid restoring the older writer after new Core evidence exists. For a regression, prefer an exact-head forward fix that retains the field and fail-closed funding check. Preserve original recovery, financial history, broker observations, and private account documents regardless of release outcome.
