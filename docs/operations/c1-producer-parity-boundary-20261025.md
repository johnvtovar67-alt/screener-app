## Concrete failed invariant

**The complete current observation sequence and timestamps are generated by arbitrary `/api/top5` requests, not by the existing cron schedule. A side-effect-free read cannot continue creating those observations.**

- `pages/api/top5.js:654` builds a broad snapshot on a cold/expired process, bypasses its five-minute broad cache for each `verificationPass > 0`, and groups only same-process inflight requests with the same session/pass. Warm-memory behavior is currently part of the acquisition sequence.
- `pages/api/top5.js:786` also rotates the bounded fundamentals priority by `verificationPass * 24`; dropping the pass is not equivalent acquisition coverage.
- `pages/api/top5.js:970` records at `new Date().toISOString()` during each eligible GET, even when reusing a snapshot. Same-snapshot successful recording is suppressed only for 30 seconds, so a repeated cached GET 31 seconds later changes `lastMarkAt`.
- `pages/api/top5.js:1146` always awaits broad performance observation regardless of which theme is read. Public direct consumers therefore also contribute observations. Making only the browser call a new POST before GET would not preserve existing public GET contract.
- `lib/performanceLedger.js:52` uses the observation timestamp for signal entry, session/day, state history, last marks, and horizon filling; intermediate marks update extrema. It cannot reconstruct omitted prices/times from the final snapshot.
- `lib/opportunityDecision.js:110` uses a 6.5-hour Strong Buy and 36-hour Buy memory, which feed eligibility/timing verification. `strongBuyPersistence` seeds these from exact ledger timestamps. Shifting acquisition/earned timestamps changes membership at the edge, even with the same final price.
- `vercel.json` runs the index producer every 15 minutes during configured weekday hours and discovery nightly. Neither currently calls the broad route, and neither describes arbitrary request observations.
- The existing PR326 conditional-write protection preserves acknowledged ledger rows by rejecting stale writers; it is not a cross-instance producer queue, exactly-once observation log, distributed acquisition cache, or immutable snapshot stream.

## Alternatives assessed

1. Daily producer: fails entry/extrema/return/transition/timestamp parity (prior evidence independently reproduced).
2. Existing 15-minute producer: fails the same invariants and hysteresis, concretely demonstrated above.
3. Faster polling: still cannot guarantee arbitrary request timestamps, pass-specific coverage, or existing per-instance cache transitions; adds observations on intervals where no request formerly occurred.
4. Producer triggered/enqueued by GET: can preserve a request-driven trigger but violates the immutable read requirement; durable enqueue is itself a write. Conditional writes alone do not resolve this.
5. New owner/browser POST followed by immutable GET: preserves a normal refresh intent but changes public GET callers, request timing, acquisition ownership and potentially observations during the extra round trip. The authorized condition is exact parity, not approval to silently retire/alter GET behavior. Requires an explicit producer trigger/public-interface/timing contract or a supplied complete authoritative observation stream that preserves the current sequence.
6. Claiming an immutable artifact as sole authority after one mechanical extraction: unsupported; it changes current global-memory cache/hysteresis behavior without a cross-instance replay oracle. No scaffold is added.

## What unblocks

Either provide a complete trusted acquisition/observation stream carrying all existing request-driven events, exact timestamps/pass-specific source evidence and current ordering/cache semantics, then prove full output/memory/ledger parity; or explicitly choose a new trigger/public-interface/timing policy, accepting the enumerated changes. No daily-only policy is authorized. No pause/disable/change of normal crons is warranted.
